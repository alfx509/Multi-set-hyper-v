# ASTER bends Windows internals to give seats real screens

ASTER (by IBIK) does not use RDP, virtual machines or streaming. It gives each workplace a **real Windows logon session**, and a **kernel-mode driver, `mutenx.sys`**, sends that session's picture to a real GPU output and takes its input from specific USB keyboards and mice. This is why games run at the monitor's own speed and not at the RDP limit of 30 or 60 fps. The price is high. Microsoft's own documentation says that **the monitors of a WDDM GPU always belong to the console session**, so ASTER must change Windows behavior in ways Microsoft does not document. As a result, ASTER needs a new release for almost every big Windows update, it has broken boot and Secure Boot several times, and some anti-cheat systems block it. No public reverse-engineering of ASTER exists, so the exact hooks are unknown. No open-source project on Windows does the same thing today. For MultiSeat, a fully ASTER-like design (own kernel hooks into the graphics stack) is not realistic for an open-source project. A realistic path is to keep real separate sessions, but replace the RDP display with a faster local frame path, and to be honest with users about Windows Pro licensing.

## ASTER runs one real Windows session per seat, not RDP

ASTER describes itself as a **"multi-user extension of the Windows kernel"**. Its manual says it can only be turned on or off with a reboot ([ASTER XP manual](https://www.ibik.ru/download/manual/xp/ru/manual.htm)). IBIK says it works **without thin clients, virtual machines or terminal stations, and without the local network** ([ibik.ru](https://www.ibik.ru/)). Its promo material says that **the RDP protocol is not used** ([IBIK promo PDF](https://www.dokwiki.ibik.ru/_media/ru/promo_aster.pdf)).

Outside observation confirms that the seats are real Windows sessions. A developer of the Veyon classroom tool looked at an ASTER PC with the normal Windows session API (WTS). Seat 1 is the normal session called **"Console"**. Every extra seat is a separate session with the WinStation name **"Multiseat"**. Seen from the system services, the extra sessions show the status "disconnected", even though people are using them ([Veyon forum](https://veyon.nodebb.com/post/3830)). This is a strong clue. ASTER probably creates the sessions with the same Windows machinery that Fast User Switching and Remote Desktop use. But it does not "connect" them through the normal RDP path. Instead, its own driver feeds them screen and input. This is an inference; IBIK has never published its design.

The ASTER changelog also shows that it works with sessions directly. It has items such as "changes in user session management", a per-seat lock screen and SharedPCMode, and a warning when one Windows account logs on at two seats ([ASTER version history](https://www.dokwiki.ibik.ru/en/v2/core/history)). A user once claimed ASTER uses Windows MultiPoint. Another user corrected this: MultiPoint is RDP-based, and ASTER uses plain Windows sessions ([ibiksoft community](https://ibiksoft.com/community/problems-and-solutions/does-anyone-know-how-aster-works/)).

### How a seat gets its own monitor

Before you turn ASTER on, you must **extend the Windows desktop over all monitors and set each monitor's resolution** ([ASTER FAQ](https://dokwiki.ibik.ru/en/v2/core/faq/faq_other)). In the ASTER Control program, each monitor is a **"video surface" of a video card**, numbered by card and output ([ASTER config guide](https://dokwiki.ibik.ru/en/v3/core/ugd/ugd_config)). You drag monitors, keyboards, mice and sound devices to each seat. This tells us how it most likely works. ASTER does not create new display adapters. It takes the outputs that the GPU driver already made for the extended desktop, and gives each output to a different session. The changelog supports this. It lists work on **"WDDM 2.2, 2.3, 2.4"**, **"WDDM 2.5/2.6 (DirectX 12)"** and **"WDDM 2.7"**, plus **"GPU isolation code"** and **"code of interaction with DirectX"** ([ASTER version history](https://www.dokwiki.ibik.ru/en/v2/core/history)). A normal display driver would not need this. So ASTER almost certainly hooks the Windows graphics kernel (dxgkrnl and win32k). Nobody has published proof of exactly which parts it patches.

This design also explains the known display problems. Programs that change the screen resolution may fail. Games may not enter exclusive fullscreen, so IBIK advises windowed mode ([ASTER FAQ](https://dokwiki.ibik.ru/en/v2/core/faq/faq_other)). ASTER also accepts extra monitors from **DisplayLink, FrescoLogic USB adapters, Miracast and spacedesk** ([ASTER FAQ: hardware](https://dokwiki.ibiksoft.com/en/v3/core/faq/faq_config)). IBIK even recommends the open-source **virtual-display-rs** IddCx driver to make virtual monitors for remote seats ([IBIK wiki](https://dokwiki.ibiksoft.com/en/v3/core/article/virtualdispalys)).

### Input, audio and USB per seat

Each seat gets specific keyboards, mice, touch screens and webcams by device. Audio devices can be given to one seat or **shared by several seats**. A **whole USB hub** can be given to a seat. Then every device on that hub follows the seat, and other seats are **denied access to USB disks and CD/DVD drives** on that hub ([ASTER config guide](https://dokwiki.ibik.ru/en/v3/core/ugd/ugd_config)). There are limits. Joysticks, touch input, Xbox controllers and eToken/ruToken have at times worked **only on the first seat** ([ASTER FAQ: hardware](https://dokwiki.ibiksoft.com/en/v3/core/faq/faq_config)). This suggests that ASTER redirects mainly the keyboard and mouse driver stacks. How it routes input and audio inside Windows is not public.

### Full GPU, but shared

ASTER does not split the hardware. Every seat can use the whole CPU and GPU ([Unraid forum](https://forums.unraid.net/topic/120636-options-for-multiseating-besides-aster)). The picture goes straight from the GPU to the monitor, with no encode and no network. That is the reason for local speed. But two heavy games share one GPU. One user found a second player **"costs more than half the performance"** on a GTX 1070, with the CPU often the bottleneck ([ASTER English forum](https://www.forum-en.ibik.ru/viewtopic.php?t=3504)). Most users report **a stable 60 fps on two seats**, and a third game copy needed lower settings ([ASTER Russian forum](https://www.forum.ibik.ru/viewtopic.php?f=7&p=47448)). No one has published tests above 60 Hz, or with G-Sync/FreeSync, on a second seat. So "no 60 fps cap" is very likely true by design, but it is not proven by measurement.

## One signed kernel driver that fights every Windows update

ASTER has few parts. The core is **`mutenx.sys`**, a 64-bit **kernel-mode driver** (service `MUTENX_SERVICE`) in `C:\Windows\System32\drivers`. Next to it are the user-mode service **`mutesv.exe`**, the GUI **`mutectl.exe`** and the setup wizard **`mutewizard.exe`**, installed in `C:\Program Files\ASTER` ([FAQ: ASTER and other software](https://dokwiki.ibiksoft.com/en/v2/core/faq/faq_soft); [Advanced Uninstaller](https://www.advanceduninstaller.com/ASTER-v2_52_2-f36447a420d78f714916be9ac09e9725-application.htm)). On Windows XP the part was `mute32.dll`. Only one driver is named in public. It is not known whether hidden filter drivers also exist.

### Signing history: from test mode to Secure Boot

Old builds of `mutenx.sys` are **signed by "IBIK, LLC" with a GlobalSign code-signing certificate**. One build from 2015 has a certificate valid from January to December 2015 ([herdProtect](https://www.herdprotect.com/mutenx.sys-23ca896b933ac76b66bd2b8147f8645555b0e3eb.aspx)). This is a normal company signature, not a Microsoft (WHQL) signature. The history shows the problems this caused:

| Date | What happened |
|---|---|
| Jan 2010 | The first ASTER for Windows 7 x64 needed **test-signing mode**. Without it, Windows would not boot because of the unsigned `mutenx.sys` ([IBIK forum](https://www.forum.ibik.ru/viewtopic.php?t=26036)). |
| 2017 | On Windows 10 build 15063, Windows **would not boot with Secure Boot on** and ASTER enabled ([ASTER FAQ](https://dokwiki.ibik.ru/en/v2/core/faq/faq_other)). |
| Feb 2019 (v2.25) | Secure Boot no longer had to be off, **except on Server 2016+ and on systems that require WHQL** ([ASTER version history](https://www.dokwiki.ibik.ru/en/v2/core/history)). |
| Aug 2025 (v2.70) | IBIK says ASTER can now run **with Secure Boot on** ([ibik.ru changelog](https://www.ibik.ru/ru/history-change/)). |
| Sep 2026 (v2.70.6) | Instructions added for **"error 2(31), a conflict with Windows 11 security policy"** ([ibik.ru changelog](https://www.ibik.ru/ru/history-change/)). |

So the answer is: **yes, kernel-mode; signed by IBIK, but for most of its life not with a Microsoft signature.** How v2.70 became Secure Boot compatible is not documented. The "Windows 11 security policy" error may be Memory Integrity (HVCI), Smart App Control or the vulnerable-driver blocklist. That is a guess. A driver that patches kernel graphics code would clash with Memory Integrity, but this is not confirmed.

### Windows updates are the biggest weakness

ASTER releases follow Windows builds almost one for one. Windows 10 build 14393 stopped Windows from booting with ASTER v2.12 ([ibik.ru notice](https://www.ibik.ru/windows-10-build-10-0-14393)). Update KB3172985 did the same to v2.11 ([ibik.ru notice](https://www.ibik.ru/attention-incompatible-update-of-windows-10)). After the 1703 update, monitors vanished ([ibiksoft community](https://ibiksoft.com/community/problems-and-solutions/monitors-vanish-from-system-with-1703-update/)). Windows 11 build 26100.3037 caused a **blue screen**, fixed in v2.60.3. Windows 11 24H2 needed a monitor fix in late 2025 ([ASTER RU history](https://www.dokwiki.ibik.ru/ru/v3/core/history); [ibik.ru changelog](https://www.ibik.ru/ru/history-change/)). In February 2026 a user on Windows 11 Pro reported that, after an update, the second seat **lost its keyboard and mouse every 10–20 minutes**, with no answer from staff ([ibiksoft community](https://ibiksoft.com/community/main-forum/second-workplace-randomly-loses-input-devices-after-windows-update-aster-2-60-4/)).

IBIK's answer is to control updates. ASTER **forces Windows Update to defer updates** ([ASTER version history](https://www.dokwiki.ibik.ru/en/v2/core/history)), and since v2.70.5 (July 2026) it **blocks Windows updates that affect stability** while it runs ([ibik.ru changelog](https://www.ibik.ru/ru/history-change/)). It also **blocks installing display drivers** while ASTER is on ([ASTER version history](https://www.dokwiki.ibik.ru/en/v2/core/history)). This is the clearest public sign that ASTER depends on **undocumented, build-specific Windows internals**. A driver that used only documented interfaces would not need a new version for each Windows build.

## Editions, seat counts and licensing stay in a grey zone

ASTER today supports **Windows 8, 8.1, 10 and 11**, and since v2.70 again **Windows 7**. Server 2008 R2 and later has only "formal" support and "has not been tested" ([ASTER FAQ: hardware](https://dokwiki.ibiksoft.com/en/v3/core/faq/faq_config)), although IBIK has shown Server 2022 and 2025 in practice. IBIK documents no Home vs Pro limit. One user says it works on **Windows Home** ([Hacker News](https://news.ycombinator.com/item?id=38585526)).

Seat numbers differ by source. The licence allows **no more than 12 seats per PC** ([ASTER licence terms](https://www.dokwiki.ibik.ru/en/v3/core/ugd/ugd_terms)). The Russian website still says **"up to 6 users"** ([ibik.ru](https://www.ibik.ru/)). In 2025 IBIK tested **16 seats** on Windows Server 2025 with one Quadro P2200 and 15 USB docks, using a dealer-only licence ([ibiksoft.com](https://ibiksoft.com/successful-testing-of-16-workplaces-on-a-single-computer-using-aster-software/)). Real users almost always run **2 or 3 seats** ([Steam Community](https://steamcommunity.com/discussions/forum/1/3006676913257769697); [Hacker News](https://news.ycombinator.com/item?id=38585526)). IBIK suggests about **500 MB of RAM per seat** ([ASTER FAQ: hardware](https://dokwiki.ibiksoft.com/en/v3/core/faq/faq_config)).

Client Windows normally allows only one active local session. **IBIK never explains how it gets around this limit, and never talks about Microsoft licensing.** The Windows 11 licence terms forbid you to **"work around any technical restrictions or limitations in the software"**. They also say that hardware or software that **multiplexes or pools users does not reduce the number of licences you need** ([Windows 11 OEM licence terms](https://microsoft.com/content/dam/microsoft/usetm/documents/windows/11/oem-(pre-installed)/UseTerms_OEM_Windows_11_English.pdf)). The "simultaneous use over a network" clause does not clearly cover local seats. But the overall reading is that several people using one client Windows at once is a licensing problem. Microsoft's own multi-user client, Windows 11 Enterprise multi-session, is only for Azure Virtual Desktop ([Microsoft licensing guide](https://www.microsoft.com/licensing/guidance/Windows-11-Licensing-for-Virtual-Desktops)). I found no public case of Microsoft acting against a multiseat vendor. This is not legal advice.

## Anti-cheat, GPUs and launchers limit what ASTER can run

**Kernel anti-cheat is the most common failure.** Users report that **EasyAntiCheat** will not allow a second copy ([ibiksoft community](https://ibiksoft.com/community/games/how-to-play-multiple-instances-of-easy-anticheat-games/)). With **BattlEye**, opening a game on one seat closes it on the other ([ibiksoft community: Fortnite](https://ibiksoft.com/community/games/fortnite/)). With **Valorant's Vanguard**, the second seat's mouse stopped working once one copy ran ([ibiksoft community: Valorant](https://ibiksoft.com/community/games/is-there-a-way-to-run-two-instances-of-valorant-on-aster)). EA's **Javelin** anti-cheat flags ASTER itself, so even one EA game can refuse to start ([EA forums](https://forums.ea.com/discussions/apex-legends-technical-issues-en/security-violation-error-aster-ibik-blocked-by-javelin-anticheat/13762744)). Many non-anti-cheat games work, such as Minecraft, Witcher 3, Borderlands, Civ VI and Ubisoft titles ([ASTER Russian forum](https://www.forum.ibik.ru/viewtopic.php?f=7&p=47448)). Steam used to allow only one client per Windows. ASTER v2.31 (July 2022) added a built-in fix so Steam runs on several seats **without Sandboxie** ([ASTER version history](https://www.dokwiki.ibik.ru/en/v3/core/history)).

**GPU support is narrow.** Only **NVIDIA GeForce, AMD Radeon and Intel integrated** graphics with a WDDM driver are supported. **SLI/CrossFire is not allowed.** On hybrid laptops the discrete GPU cannot be used. Low-level tools such as **GeForce Experience, MSI Afterburner and RivaTuner** should not be installed ([ASTER FAQ: hardware](https://dokwiki.ibiksoft.com/en/v3/core/faq/faq_config)). Users also advise keeping all seat monitors on the same GPU ([Online Tech Tips](https://www.online-tech-tips.com/play-split-screen-multiplayer-on-pc/)). Small bugs are common: a second monitor that does not sleep, missing speakers, Steam Controller disconnects, and Cisco VPN refusing more than one user ([ASTER Russian forum](https://www.forum.ibik.ru/viewtopic.php?f=7&p=47448)). One user summed it up: you cannot get two full computers from one; there are compromises.

## Open-source projects solve only parts of the problem

Most old commercial rivals are dead. **SoftXpand** stopped at Windows 7 ([AlternativeTo](https://alternativeto.net/software/softxpand/about)). **BeTwin** stopped at Windows 8.1 ([AlternativeTo](https://alternativeto.net/software/betwin-es/about)). Microsoft **stopped developing MultiPoint Services** after Windows Server 2016 ([Microsoft Learn](https://learn.microsoft.com/he-il/windows-server/get-started/removed-deprecated-features-windows-server-2019)). MultiPoint itself was built on Remote Desktop Services, with class filter drivers that scoped devices to stations ([Microsoft Learn: MultiPoint stations](https://learn.microsoft.com/en-us/previous-versions/windows-server/it-pro/windows-server-2019/remote/multipoint-services/multipoint-services-stations); [Microsoft Learn troubleshoot](https://learn.microsoft.com/troubleshoot/windows-client/performance/cannot-scan-device-connected-usb)). **NComputing** still sells thin clients over the network, not local GPU seats ([NComputing](https://support.ncomputing.com/portal/en/kb/articles/feature-comparison-chart-for-vspace-pro-enterprise-edition-lts-edition-and-ads-edition)).

**No open-source project on Windows gives each session its own physical monitor.** The open tools each solve one part:

| Project | What it solves | What it does not solve |
|---|---|---|
| **Nucleus Co-op** (GPL-3.0) + **ProtoInput** (MIT) | Many game copies in one desktop; per-device keyboard/mouse routing by hooks ([Nucleus](https://github.com/SplitScreen-Me/splitscreenme-nucleus); [ProtoInput](https://github.com/Ilyaki/ProtoInput)) | One Windows user only; no separate Steam accounts |
| **Duo** (DuoStream) | Separate sessions per player via TermWrap, streamed with Sunshine/Moonlight; paid tier up to 500 Hz ([Duo](https://github.com/DuoStream/Duo)) | Streamed, not direct scan-out; free tier capped at 30 Hz; no open licence stated |
| **RDP Wrapper / TermsrvPatcher** | Unlocks several sessions on client Windows ([rdpwrap](https://github.com/stascorp/rdpwrap/issues); [TermsrvPatcher](https://github.com/geissbuehler/TermsrvPatcher)) | Breaks on updates; licence problem; display still RDP |
| **Interception** | Kernel filter that tells keyboards and mice apart ([node-interception docs](https://rami-sabbagh.github.io/node-interception/index.html)) | Input only; old signing, current status unverified |
| **Easy-GPU-PV** (Hyper-V GPU-P) | Full separate VM per seat on Windows Pro, one GPU shared ([Easy-GPU-PV](https://github.com/jamesstringerparsec/Easy-GPU-PV)) | No Vulkan; needs streaming; archived; anti-cheat blocks VMs |
| **VFIO on unRAID/Proxmox** | Native speed, direct monitor, one GPU per VM ([Unraid blog](https://unraid.net/blog/7-gamers-in-1-tower-behind-the-scenes)) | Linux host, not Windows Pro; one GPU per seat |
| **Linux systemd-logind** | Real built-in multiseat: `loginctl attach` binds a GPU and devices to a seat ([loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html)) | Linux only; usually one GPU per seat |

Anti-cheat also blocks VMs more and more. BattlEye kicked an unRAID user with "disable the virtual machine" ([unRAID forum](https://forums.unraid.net/topic/133384-blocked-by-battleye-for-virtual-machine)). So virtualization is not a safe answer for competitive games either.

## Building an ASTER-like system means fighting documented Windows rules

### What Windows documents, and the core blocker

Microsoft is clear. **"The display capacities of a WDDM GPU are always associated with the console terminal."** A local monitor "will only display the console terminal" ([Microsoft Learn: consoles vs terminals](https://learn.microsoft.com/en-us/windows/win32/termserv/consoles-vs-terminals)). All local input devices are also attached to that one console. Any other session gets screen and input only through a **"remote terminal"** made by a protocol provider such as RDP. To get graphics out of such a session, you need a **remote Indirect Display Driver (IddCx)**. The OS accepts the remote IDD flag **only for devices the OS remote desktop stack created** ([Microsoft Learn: IddCx 1.4 remote IDDs](https://learn.microsoft.com/windows-hardware/drivers/display/iddcx1.4-updates-for-remote-idds)). The good news is that third parties may write their own protocol: **"You can create your own protocol"** with the Remote Desktop Protocol Provider API ([Microsoft Learn: protocol provider API](https://learn.microsoft.com/en-us/windows/win32/termserv/custom-remote-desktop-protocols)).

So there are three ways to build an ASTER-like product. The first is a **custom protocol provider plus a remote IDD**, using documented APIs. The session renders on the real GPU, and its frames are then copied to a seat monitor. The second is **undocumented kernel hooks** that let a non-console session own a GPU output directly. This is what ASTER most likely does. The third is **one VM per seat**.

### Required components and how documented they are

| Component | Job | Documented? | Kernel or user mode |
|---|---|---|---|
| Several interactive sessions | One Windows session per player | Yes on Server/RDSH. On Pro only by patching termsrv (RDP Wrapper style) | User mode patch |
| Session display, documented path | Custom protocol provider + remote IddCx; frames copied to a full-screen presenter on the seat's monitor | Yes (APIs public). Whether a third-party provider on Pro passes the "OS stack" check is not confirmed | IddCx is user mode (UMDF) |
| Session display, ASTER path | Give a GPU output directly to a non-console session | **No.** Needs hooks in dxgkrnl/win32k; changes every build | Kernel |
| Input routing | Catch each keyboard/mouse below `kbdclass`/`mouclass` and send it to its session | Filter samples (kbfiltr/moufiltr) are public; injecting into a session uses the provider input channel | Kernel filter (or user-mode Raw Input, less exact) |
| Audio per seat | Seat sees only its own headset | **No public API** for non-RDP providers | Probably virtual endpoint driver |
| USB storage per seat | Hide other seats' drives | No public API; needs filter drivers (MultiPoint used class filters) | Kernel |
| Seat manager | Login screen per seat, config GUI, recovery | Normal Windows service | User mode |

### Driver signing in late 2026

Since Windows 10 1607 with Secure Boot on, Windows **loads no new kernel driver unless Microsoft signed it** through the Partner Center. You need an **EV code-signing certificate** on the account, then **attestation signing** or full **WHCP/HLK certification** ([Microsoft Learn: driver signing policy](https://learn.microsoft.com/windows-hardware/drivers/install/kernel-mode-code-signing-policy--windows-vista-and-later-); [Microsoft Learn: code signing requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs)). **Since April 2026, Windows no longer trusts cross-signed certificates by default** for kernel drivers ([Microsoft Learn: cross-certificates](https://learn.microsoft.com/windows-hardware/drivers/install/cross-certificates-for-kernel-mode-code-signing)). Attestation-signed drivers for retail are **not shipped through Windows Update**, and Microsoft's docs now describe attestation as being "for testing scenarios" ([Microsoft Learn: attestation signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation)). Watch this; it may get stricter. The new "custom kernel signers" feature needs a clean install and your own Secure Boot keys, and Microsoft made it hard **on purpose** to stop consumer use ([Microsoft Learn: custom kernel signers](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/custom-kernel-signers)). The **vulnerable driver blocklist** is on by default since Windows 11 22H2, and Memory Integrity is on by default on most new PCs ([Microsoft Learn: driver block rules](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/microsoft-recommended-driver-block-rules)). So every driver must be HVCI-compatible.

**Test-signing mode is not an option for users.** It needs Secure Boot off ([Riot support](https://support.riotgames.com/pl-pl/riot/security/restore-windows-security-to-normal-state)), and anti-cheats like FACEIT can require proof that the PC booted with Secure Boot and no unauthorized software ([FACEIT support](https://support.faceit.com/hc/en-us/articles/22851956652956-Known-issues-with-Anti-Cheat-Requirements)). For an open-source project this means: someone must own an EV certificate and a Partner Center account and sign every release. Community forks cannot ship their own kernel drivers. User-mode drivers such as IddCx still need a signed package, but avoid most kernel risk.

### The main risks

The first risk is **update breakage**: an undocumented hook path will break with Windows updates, as ASTER's ten-year history shows. The second is **licensing**: unlocking several sessions on Pro conflicts with the "work around technical restrictions" clause. The third is **signing**: a kernel driver needs an EV certificate and Microsoft signing, and the rules got stricter in 2026. The fourth is **anti-cheat**: EA already flags ASTER, and kernel anti-cheats dislike unknown kernel drivers. The fifth is **frame rate on the documented path**: RDP sessions are capped at **30 fps by default and 60 fps with `DWMFRAMEINTERVAL`**, and users say even that stopped working after 23H2 ([Microsoft Learn: 30 FPS limit](https://learn.microsoft.com/en-us/troubleshoot/windows-server/remote/frame-rate-limited-to-30-fps); [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1403785/after-upgrading-to-23h2-the-frame-rate-is-still-on)). It is **not documented** whether a custom protocol provider gets the same DWM cap. Duo's paid tier reaches up to 500 Hz in separate sessions ([Duo](https://github.com/DuoStream/Duo)), which suggests that the cap can be avoided, but Duo uses custom patches that are not described.

## Conclusion

ASTER's speed does not come from a clever display trick that MultiSeat can simply copy. It comes from a decision to break a documented Windows rule ("monitors belong to the console") inside the kernel, and to pay for that decision with a release for every Windows build, update blocking and signing trouble. A small closed company can do this full-time. An open-source project with volunteers, and with no EV certificate, very likely cannot do it safely. The most useful insight is that the user's real complaint has two parts. The first is the **frame rate**, which is a problem of the RDP display path, not of separate sessions. The second is the **"not a local environment" feeling**, which comes from the mstsc client window and RDP devices. Both can be improved without kernel hooks into the graphics stack. Only "direct scan-out with zero copy on Windows Pro" really needs ASTER's undocumented approach.

## Recommendation for the MultiSeat project

**1. Do not try to clone ASTER's kernel graphics hooks.** It needs undocumented dxgkrnl/win32k changes, a Microsoft-signed kernel driver, an EV certificate, and fixes after almost every Windows update. It would also put users at risk of boot failures and anti-cheat bans. Write this clearly in the README and in `docs/troubleshooting.md`, so users understand why.

**2. Keep real separate Windows sessions; they are the right base.** Each player keeps their own Windows user, Steam account and saves. This part of MultiSeat already matches ASTER.

**3. Replace the RDP display path, step by step.**
- **Step A (fast, user mode):** Stop using the mstsc window as the player's screen. Inside each player session, run a small helper that captures that session's desktop on the GPU, and show it full-screen on the player's monitor with a borderless presenter on the console. Measure first whether capture in a non-console session can go above 60 fps. Duo shows it is possible with Sunshine-style capture. Avoid video encoding where you can, because everything is on the same PC.
- **Step B (documented, larger work):** Write a **custom Remote Desktop Protocol Provider plus a remote IddCx driver**. This removes RDP completely. The IDD gets each session's frames directly, and the provider's input channel delivers each player's keyboard and mouse. This is the Microsoft-documented way, and it is close to how MultiPoint worked. Before you build all of it, make a small prototype that answers two open questions: does Windows accept a third-party provider's remote IDD, and is the DWM frame cap applied to it?

**4. Input:** Keep user-mode Raw Input routing as the default (ProtoInput proves it works). Add a kernel keyboard/mouse class filter only if needed, and only when the project has an EV certificate and a Partner Center account for attestation signing. Make every driver HVCI-compatible. Never ship test-signed drivers to users.

**5. Windows Pro:** Be honest. On Pro, several sessions need a termsrv patch (RDP Wrapper/TermWrap style). This breaks on updates and conflicts with the Windows licence terms. Offer it only as an **optional, clearly labeled "experimental, at your own risk" mode**, keep Server/RDSH as the supported mode, and add a check that refuses to start on an unknown termsrv.dll build instead of crashing.

**6. Give users a second option for Pro:** Add an optional **Hyper-V GPU-P mode** (Easy-GPU-PV style) for players who want full isolation on Windows Pro, with the clear warning that Vulkan does not work and anti-cheat may block VMs.

**7. Tell the user the truth today.** If the user needs ASTER behavior on Windows Pro right now, ASTER itself is the only working product, and it has the same licensing grey area. MultiSeat can get much closer than it is now (higher frame rate, no RDP window), but not identical without kernel hooks.
